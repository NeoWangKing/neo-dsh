# AGENT.md — 在这个仓库里干活前先读这个

> 中文速览：Neo DSH 是 DeepSeek Harness 的桌面套件（Electron 外壳 + 第一方插件 + agent 预设 + profile）。
> 规矩：改动先在 **dev 窗口**里给人看 → 人确认 → 才 commit；**只有用户说了才发版**；发版 = 推 tag，**由 GitHub Actions 打包**，
> 不要在本地交叉打包（会塞错平台的 Node 运行时）。改行为的改动必须带测试；中英文文档要一起改；本文件要在同一次改动里更新。

## What this repo is

Neo DSH — a desktop suite around the DeepSeek Harness. The shell is Electron; everything
that makes it *this* product (plugins, agent preset, profile, resources) lives here. The
harness itself is vendored under `apps/desktop/node_modules/@deepseek-ai/` (0.2.0-rc.2;
see "The 0.2 harness migration" below before touching those versions).

| Path | What lives there |
| --- | --- |
| `apps/desktop/src/` | the shell: home resolution/migration, host spawn + watchdog, port guard, safe mode, proxy, settings routes. No Electron imports outside `main.mjs`, so the logic stays unit-testable. |
| `apps/desktop/test/` | unit suites for the above (plain node, run by `pnpm test`). |
| `plugins/*/` | first-party host plugins (`dsh-activity-line`, `dsh-desktop-settings`, `dsh-smart-approval`). |
| `presets/*/` | agent presets. `liangshen` is the shipped one; a preset dir is read as one `agent.cordis.yml` **plus** the `.mjs` plugins it names (`./tool-bootstrap.mjs` …). |
| `apps/desktop/resources/` | build output that ships in the app: `profile-web/` (profile files + patch layer + plugin `vendor/`), `presets/`, `icon.png`, `settings.defaults.yaml`. Generated by `scripts/build-resources.mjs` — never edit by hand. |
| `scripts/` | `build-resources.mjs` (assemble resources), `patch-harness.mjs` (vendored patches), `vendor-npm-plugin.sh` (vendor an npm plugin with its dependencies into `vendor/`), `fetch-node.mjs` (the Node runtime each platform ships), `check-node.mjs`, `dev-window.sh`, `install-release.sh` (install a published release into a local prefix; verifies the sha256, backs up the old tree, refuses while the app runs). |
| `docs/development*.md` | the human-facing development notes, **English and Chinese kept in step**. |
| `docs/roadmap.md` | the user's own backlog (Chinese only, by design): planned work with the implementation traps already noted. Read it before proposing features; add to it when the user asks for something "later". |
| `.github/workflows/build.yml` | CI: builds linux-x64 / macos-arm64 / windows-x64 and attaches artifacts to the release. |
| `.github/workflows/patch.yml` | CI: publishes a **hot patch** (`patch.json` + `payload-<id>.tar.gz`) onto the fixed release tagged `patch`. Marked prerelease so it never takes the "latest release" slot. |

## Non-negotiables (learned the hard way)

1. **Show before you commit.** Every user-visible change goes through a dev window
   (`bash scripts/dev-window.sh`, port 3199, throwaway home) and the user looks at it.
   Then commit. **Never release without being asked.** Releases are batched.
2. **Update this file in the same change.** If a change alters how the product behaves, how
   it is built, or what an agent should know, `AGENT.md` is part of that change, not a
   follow-up.
3. **Behaviour changes carry tests.** Add them to the `pnpm test` chain in `package.json`.
   Evidence over prose: quote the log line, the test output, the digest — not "should work".
   A real check catches real bugs: the mac build shipped a Linux `node` once and only the
   smoke test noticed (`spawn ENOEXEC`).
4. **Don't rewrite files under a running app.** The client watches the bundles it serves and
   reloads a module the moment it changes; a half-written file takes the UI down
   (`scripts/patch-harness.mjs` writes through a temp file + rename for exactly that reason).
   Patch an installed tree only when the user is about to restart, and say so.
5. **Never leave state behind.** Close dev windows, and clean `/tmp/neo-dev-*`. A headless
   run pointed at the app's own `DSH_HOME` writes a *real session* into the user's sidebar —
   give verification runs their own `DSH_HOME` (see `docs/development*.md`).
6. **Both languages, or neither.** Docs and release notes exist in Chinese and English;
   update both in the same commit.
7. **Config before patches.** Prefer a profile patch row (`plugins/*/cordis.patch.yml`,
   `resources/profile-web/cordis.patch.yml`) over editing vendored code. Patch the harness
   only when there is no seam, keep the patch small, and make it fail loudly when its anchor
   moves (`scripts/patch-harness.mjs`).

## How a change is made

```sh
pnpm test                      # seconds; every suite must pass
bash scripts/dev-window.sh     # the user looks at :3199 (throwaway home, isolated Electron profile)
git add -A && git commit       # conventional commits: feat(scope): … / fix(scope): … / docs(scope): …
```

**Commit freely; packaging is the one step that waits.** A change is not finished until it is
committed and pushed, so do that on your own. Tagging, building artifacts, publishing a release
and installing over the running app are the user's call alone — never tag or package without an
explicit order ("发" / "打包" / "发版"). The dev window is how a change gets looked at, not a gate
on committing it.

Commit scopes in use: `smart-approval`, `permission`, `models`, `icon`, `shell`,
`patch-harness`, `docs`, `release`.

## Environment fixes the installer applies

An install may fix the *machine*, not just the tree: `scripts/install-release.sh` ends with
`ensure_monospace_nerd_font`, which points fontconfig's generic `monospace` at
`JetBrainsMono Nerd Font Mono` when that face is installed and the family does not already
resolve to it (idempotent, backed up, skipped when the face is absent).

Why: the built-in terminal and every other program asking for `monospace` rendered Nerd
icons as empty boxes because fontconfig resolved the generic family to Noto Sans Mono, which
has no Nerd glyphs. Two rounds were spent editing the terminal's CSS variable and its xterm
`fontFamily` default before `fc-match monospace` showed the real cause — **for a glyph problem,
ask fontconfig first**.

## What an update may and may not touch

An update replaces **our code**. It must never decide what the user owns.

- **Never** change which plugins the user has installed or enabled, and never change their
  settings. `dsh.profile.bundles` in the live profile is the user's list, not ours.
- Anything that writes a profile **snapshots it first** (`patch-state/profile-snapshots/`,
  newest ten kept — see `snapshotProfile` in `main.mjs`). A repair that cannot be undone is
  not a repair.
- Retirement is limited to bundles this app is **known** to have stopped shipping
  (`RETIRED_BY_US`), and that limit is enforced on the *record* path too (`withdrawable` in
  `profile-patch.mjs`): a name leaves only if it is on that list **and** absent from everything
  this build ships. A `file:vendor/<name>` pointer plus a marker is not proof of ownership: a
  marketplace install looks identical, and that mistake once emptied a user's plugin list.
- The set that decides retirement is the set the app materialises and owns — the shipped
  `dsh.profile.bundles` **plus** the shipped `dependencies` (`profilePresetPackages()`), which is
  `names` in `syncBundledPlugins`. Driving `reconcileBundles` from `bundles` alone made every
  plugin we ship as a dependency look withdrawn: 0.2.4 copied the community batch into the home
  and retired it in the same launch, leaving the manifest declaring dependencies whose directories
  no longer existed. `.neo-dsh-bundles.json` records that union for the same reason — the next
  launch reads it back as "what we put there", so anything missing from it looks like the user's.
- Third-party plugin managers that rewrite the profile are not shipped. `dshmarket` did that
  on every launch, which is why it is gone; the harness's own `plugin-manager` rows are the
  plugin management now.

## How the app decides there is an update

Two channels, and they must stay independent:

- **Version releases** (`v0.2.4`, built by `build.yml`) are the base. The app must always be able
  to see the newest one — that is what "跟上大版本" means.
- **Hot patches** (`patch.yml`, on the release tagged `patch`) carry small fixes. `patch-fetch.mjs`
  polls one fixed address, `releases/download/patch/patch.json`, so a patch never has to be a
  version.

`update-logic.mjs` therefore does **not** ask GitHub for `releases/latest`. GitHub defines that as
the most recently *published* release that is neither a draft nor a prerelease — a statement about
publishing order, not about versions. The moment the `patch` release was created it became
"latest": the updater read the tag `patch`, found it was not a version, and told the user the app
was up to date while v0.2.4 sat one entry below it. Instead it lists
`releases?per_page=100`, drops drafts, prereleases and any tag that is not `v<semver>`, and takes
the highest version. Two guards follow from that: the tag pattern keeps a non-version release from
ever shadowing a version, and `patch.yml` marks its release prerelease so the GitHub page agrees.

If you add a third channel that publishes a release, it must not look like a version tag.

## How a release is made

**The CI builds the artifacts. Do not build them locally.**

```sh
# 0. REFRESH FIRST — the user's standing rule: a release carries the newest harness and the
#    newest vendored payloads *as of the moment it is packaged*, not whatever was pinned when
#    the work started. Run `node scripts/deps-latest.mjs` (exits 1 listing everything behind),
#    bump `apps/desktop/package.json` (+ `pnpm --dir apps/desktop install`) and every
#    `vendor/*/package.json` it names, and re-run until it prints "every pin is current ✓".
#    `@deepseek-ai/*` moves as one lockstep set — the version npm tags `latest` for
#    `@deepseek-ai/dsh` — so a single stale pin is a real miss, not a nit. An `alpha`/`next`
#    line newer than `latest` is reported as a note and never taken automatically: moving the
#    whole app onto an alpha is the operator's call, not a preflight's.
#
# 4b. BOOT GATE — a window that renders is not a product that works.
#     Before tagging, capture the host's boot log and require it clean:
#        node scripts/check-boot.mjs <logfile>      # "✓ every plugin activated" or exit 1
#     0.2.6 shipped with "4 entries did not activate" (the chat UI plus three memory plugins)
#     while the desktop smoke test still printed SMOKE OK — it only asserted that the window had
#     a root child. A smoke test that cannot fail on a broken product is decoration.
#
# 5. CLOSE THE PATCH CHANNEL — every new version ships at zero patches.
#    A hot patch exists to fix a *released* version; the same fix must be in the repo, so the
#    next build contains it by construction. Then the channel has to be closed, or a user on
#    the new version gets offered a fix they already have:
#        gh release delete-asset patch patch.json -y     # 404 for everyone after this
#    Two rules follow, and appliesTo is not a place to be generous:
#      · a patch's appliesTo names only the versions that still need it — never a version that
#        already contains the fix;
#      · the fix lands in the repo in the same change as the patch (commit first, then publish).
#
# 1. bump both versions  (the app version tracks the harness generation: the
#    0.2.0-rc.2 harness shipped as app 0.2.0, after 0.1.17 pinned it)
#    package.json + apps/desktop/package.json : 0.1.17 → 0.2.0
git commit -m "chore(release): 0.1.16"
git tag v0.1.16
git push && git push origin v0.1.16        # the tag push is what starts the release
gh run watch                                # or: gh run list -L 3
```

`.github/workflows/build.yml` runs one job per platform (ubuntu / macos-14 / windows-latest),
each of which runs `pnpm run resources` (which applies the vendored patches *and* assembles the
resources — calling `build-resources.mjs` alone ships an app without the patches, which is
exactly what every release up to v0.1.16 did), then `scripts/fetch-node.mjs` **for its own platform** and then
`electron-builder … --publish never`, uploads the artifacts, and attaches them to the GitHub
release with `softprops/action-gh-release` — but it does **not** write the release body.

So the steps that follow the CI:

1. Confirm five assets are `uploaded`:
   `gh release view v0.1.16 --json assets -q '.assets[] | "\(.name) \(.size) \(.state)"'`
2. Write the notes the CI left empty — Chinese first, then an `## English` section:
   `gh release edit v0.1.16 --notes-file /tmp/release-notes-0.1.16.md`
3. Update the machines that run it (macOS: download the asset, check its sha256 against the
   release digest, replace `/Applications/Neo DSH.app`, smoke it).

Cross-building is a trap: `fetch-node.mjs` fetches the *host's* runtime when run without
arguments, so a mac or win artifact built from a Linux checkout ships a Linux `node` and dies
with `spawn ENOEXEC`. The CI gets this right per platform; a local attempt has to pass
`--platform/--arch` and still lacks the target's native rebuilds.

A local `pnpm run dist:linux` is fine for a smoke test before tagging: run
`DSH_DESKTOP_SMOKE=1 DSH_HOME=/tmp/… DSH_DESKTOP_PORT=32xx` against
`apps/desktop/release/linux-unpacked/neo-dsh` and expect one `SMOKE OK:` line.

## What the product ships (quick map)

- **Permission presets** (`resources/profile-web/cordis.patch.yml`, row `permission`):
  `read-only`, `workspace-write` (**default**), `danger-full-access`. A fourth preset,
  `smart-approval`, used to ship from `plugins/smart-approval/` — it answered the middle
  ground (allowlist → allow, blacklist → ask, otherwise the session's own model judges) and
  stood down whenever the policy was `never`. It is **gone as of this change**: the harness
  now ships its own 「自动授权审查」 (`@deepseek-ai/dsh-experimental-auto-review`, a switch on
  the settings page: the model decides before every tool call), which is the same idea with
  upstream's maintenance, so keeping ours would only give two overlapping answers for one
  question. The default therefore goes back to plain `workspace-write`.
- **Model catalog** (row `llm-deepseek`): one `DeepSeek-Flash` (text + images, 1M context)
  and `DeepSeek-V4-Pro`. `models` replaces the whole catalog, so both entries are written
  out; a session pinned to an id no longer listed still runs, it is just absent from the
  picker.
- **Agent preset**: `presets/liangshen` (梁神模式, id `liangshen`). Its `tool-bootstrap.mjs`
  keeps the first request on the Minimal tool pair and opens the full catalog after the
  first durable tool call; `compaction-epoch.mjs` re-arms that after a compaction. Since the
  harness moved to 0.2 the preset ships as **two pieces**, because 0.2 deleted the
  `$DSH_HOME/.agent-presets/<id>/` directory: `presets/liangshen/{agent.cordis.yml,*.mjs,
  package.json}` is the source, and `scripts/build-resources.mjs` assembles it into
  `resources/profile-web/vendor/dsh-liangshen-preset/` (a resolvable package — its own
  modules, referenced as `dsh-liangshen-preset/tool-bootstrap`) plus
  `resources/profile-web/presets/liangshen.patch.yml`, the patch layer that declares the
  preset entry. `apps/desktop/src/main.mjs` passes that layer with its own `--patch`, and
  materialises the package into the live profile's `node_modules/` **without** adding it to
  `dsh.profile.bundles` (a bundle is mounted; a preset package must only be resolvable).
- **App icon**: `apps/desktop/build/icon.png` (1024, what electron-builder derives platform
  icons from) and `apps/desktop/assets/icon.png` (512, the window icon). Both are
  composed, not drawn in code: the whale-girl art (`~/Downloads/dsh.png` on the user's
  machine) fills the canvas, with a navy `NEO` speech bubble at her upper left. The
  bubble and its tail are **one mask** — the tail's base sits inside the rounded body and
  the union is dilated for the outline — because a rectangle plus a triangle reads as two
  shapes, and a stroked-then-filled tail comes out hollow when the outline is thick
  relative to the tail. The composing script is not in the repo; redo it from the source
  art if the icon ever changes.
- **Third-party plugin, our build**: `vendor/dsh-ops-{linux,macos}/` are `dsh-ops` (Rust-backed
  native file and PTC tools) rebuilt per platform, because upstream ships Windows x64 only. It is
  a *dependency* of the shipped profile, not a bundle: `build-resources.mjs` copies the payload
  for the build host's platform (`OPTIONAL_PLUGINS`) and deletes the target when no entry claims
  that platform, the shipped manifest lists it as `file:vendor/dsh-ops`, and the app materialises
  it into the live profile without mounting it — so it shows up in the plugin page and the user
  switches it on. `profilePresetPackages()` skips any shipped dependency whose payload this
  platform does not carry, which is what keeps an absent copy from becoming a dangling `file:`
  entry. Each build records the upstream commit, the two edits (platform allowlist + `os`/`cpu`),
  and the build/stage commands in its own `BUILD-*.md`. The two copies are deliberately
  byte-identical outside `runtime/` and those two files, and `pnpm test` asserts it — that is what
  keeps an upstream bump a two-line change per platform.
- **Third-party plugin, upstream's build**: everything under `vendor/` that is upstream's own npm
  package — `dshmarket` (the plugin market) and the community batch vendored alongside it
  (`dsh-whale-widget`, `dsh-mnemon`, `dsh-context`, `dsh-cost-meter`, `cc-safety-net`,
  `@liustack/modsearch`, `@nanmicoder/dsh-agent-teams`, `@michengai/dsh-skills-manager`). The
  desktop never runs pnpm at install time, so each carries its dependencies *inside itself* as
  `vendor/<name>/node_modules/`, and its `OPTIONAL_PLUGINS` entry sets `keepNodeModules` — the tree
  copy drops `node_modules` by default, because a pnpm-installed tree is full of symlinks.
  `scripts/vendor-npm-plugin.sh` is how each one is produced and re-produced (its header explains
  the layout); `vendor/dshmarket/VENDOR.md` additionally pins that package's versions and sha256.
  A version floor can matter: `dshmarket` older than ~1.66 declares peer ranges that 0.2 skips,
  which reads as "installed but not in effect".
  **A `keepNodeModules` entry is only half the mechanism**: `.gitignore` excludes `node_modules/`
  at every level, so the tree also needs a negation rule naming that *directory* — git will not
  descend into an ignored parent, so a `!…/node_modules/**` line on its own does nothing. The two
  patterns there (`vendor/*/node_modules/` and `vendor/*/*/node_modules/`) cover unscoped and
  scoped names, so a new vendored plugin needs no `.gitignore` edit. Miss either half and the
  build, the dev window and a working-tree test all look healthy while the commit carries a plugin
  with no dependencies in it.
  **One payload has to serve all three targets.** A vendored dependency that pins `os`/`cpu`
  narrower than linux-x64 + darwin-arm64 + win32-x64 works on the machine it was vendored on and
  fails on the others. That is why `dsh-im` is *not* here: its tree carries darwin-arm64 builds of
  `@img/sharp*` and `@tencent-qqmail/agently-cli*`, so it needs a per-platform payload like
  `dsh-ops` rather than a single shared one. `pnpm test` now asserts this for every vendored
  dependency, and both that check and the `.gitignore` one were confirmed to fail when broken.
  **Verify the build the way CI does, in a fresh clone — not in the working tree.** A plugin with
  no dependencies has an empty `vendor/<name>/node_modules`, git cannot store an empty directory,
  and so the working tree has it while a clone does not. Anything that asserts its existence
  passes locally and fails the release build. (`build-resources.mjs` now compares the copy against
  the source instead, and `vendor-npm-plugin.sh` no longer creates the empty directory.)
- **Vendored patches** (`pnpm run patches:check`): open-in-app Linux icon ids, and the
  sandbox-mode check in `dsh-terminal-bash` that closes a session's persistent shells before
  a preset switch. A third one — the 智能批准 composer glyph in
  `dsh-client-ui-permission-presets` — went away with `smart-approval` itself (the harness refuses the change while a PTY is
  alive, which used to block switching presets mid-conversation).

## The 0.2 harness migration (what actually bit)

The harness is vendored, so its version is a real dependency bump, not a config change. The
route that works: resolve every `@deepseek-ai/*` dependency against **`dsh@<version>`'s own
lockstep set** (`cd /tmp && npm install --package-lock-only @deepseek-ai/dsh@0.2.0-rc.2`,
then read the resolved versions out of that `package-lock.json` — never "latest"), rewrite
`apps/desktop/package.json`, `pnpm --dir apps/desktop install`, and then expect fallout in
four places:

- **Vendored patch targets move.** 0.2 moved the permission glyph table out of
  `dsh-client-ui-conversation` into `dsh-client-ui-permission-presets` (that patch has since
  been dropped along with `smart-approval`); the open-in-app and terminal anchors happened to
  survive. A moved target is a silent miss otherwise, so `pnpm run patches:check` runs after
  `pnpm run resources` in CI.
- **Agent presets are profile entries now.** `@deepseek-ai/dsh-agent-preset-registry` takes
  only `{default, selectedDefault}`; there is no directory discovery, no `roots`, and
  `.agent-presets/` is dead. A preset is a `@deepseek-ai/dsh-agent-preset` entry whose
  `config.plugins` is the old entry list, and the default preset is that registry row's
  `config.default` (0.1.5 kept it in `settings.yaml` as `agent-presets.default`). Sessions
  record the preset **id**, so it has to stay `liangshen` or old conversations stop opening.
- **A patch cannot add an entry.** Patch rows target an existing `id` (`name`+fields) or
  append inside an entry-list config with `insert:`. A row for an unknown id is warned and
  skipped, so a new top-level entry needs `- insert: [...]` — and a root-level `insert` is
  what `build-resources.mjs` emits.
- **Every plugin package needs `name` *and* `version`.** `dsh-plugin-package-inventory-deepseek`
  reports the active plugin packages on *every* request and throws when one has no version —
  surfacing as `REQUEST_EXTENSION`/`DeepSeek request extension preparation failed` while the
  session dies at `turn/end`, with no hint that a package manifest is at fault. Ours
  (`dsh-liangshen-preset`) hit exactly that.

- **Peer dependencies are not installed for you.** A row the profile mounts can come from a
  package nothing depends on. `@deepseek-ai/dsh-deepseek-account` is a *peer* of four 0.2
  packages — the account provider, the account controller, `dsh-llm-deepseek-account` and
  `dsh-web-search-deepseek` — and no upstream package depends on it, so the app has to pin it
  itself. Without that pin every one of those rows silently fails to import, and the only sign
  is `dsh: warning: N entries did not activate … failed to import` in the host log; the
  user-visible casualty is the built-in web search, which is why it is worth a sweep rather
  than a per-symptom fix. Audit an installed tree with a `createRequire(anchor).resolve.paths(name)`
  loop over `node_modules/@deepseek-ai/*/package.json`'s `peerDependencies`; the only
  acceptable remaining gaps are packages behind `dsh-experimental-*` rows we do not mount.
- **A shipped profile must use `file:vendor/…`, never `link:`.** A dev-time `link:` dependency
  left in a live profile breaks the next time pnpm rewrites `node_modules`: pnpm replaces it
  with a relative symlink, and when that path is wrong the bundle becomes unresolvable and the
  host refuses to start (`cannot resolve profile bundle "…"`). `syncBundledPlugins` never
  touches a symlink (a symlink is treated as the user's own install), so it will not repair
  one either.

Two more 0.2 changes worth knowing: the reasoning-effort levels are `off`/`low`/`high`/`max`
(0.1.5 shipped `medium`, which the provider rejects rather than falling back —
`repairReasoningEffort` in `apps/desktop/src/boot-guard.mjs` fixes a home seeded by an older
build *before* the host starts, because the harness renames `settings.yaml` to
`settings.yaml.imported` on first read), and 0.2 enforces plugin peer ranges: the third-party
`dshmarket` in the user's home is `^0.1.x`-only and gets skipped with a loud log line until
it ships a 0.2-compatible release or the user grants an exact-version exemption.

## Shell gotchas worth keeping in mind

- **The updater uses Electron's `net.fetch`, never the global one.** Node's `fetch` carries its
  own CA list and only honours `http_proxy` when `NODE_USE_ENV_PROXY` was set *before* its
  dispatcher existed, so from a desktop launch the request goes direct — behind a proxy that
  intercepts direct traffic that fails as `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` while the browser
  (system proxy, system trust store) is perfectly happy. Measured on this machine: global fetch
  → that error; `net.fetch` → HTTP 200, from the same Electron process with the proxy variables
  removed. `update-logic.mjs` keeps `fetchImpl` injectable; `main.mjs` wires `net.fetch` in.
- **Anything the shell does over the network has the same choice to make** — the proxy env the
  shell applies to itself is not enough for Node's own HTTP stack. The patch check was the one
  path that forgot: `checkAndApplyPatch` was called without `fetchImpl`, so the app logged
  `patch: patch check skipped: fetch failed` while `curl` on the same machine fetched the very
  same manifest fine — a published hot patch sat unapplied until it was applied by hand.
  `apps/desktop/test/proxy-env.test.mjs` now asserts the wiring of all three call sites, because
  a missing `fetchImpl` is not something a behavioural test can notice.

- **The shell must be gone within a second or two of being asked to stop.** systemd's
  `DefaultTimeoutStopSec` is 90 s and it SIGKILLs whatever is left; `app.quit()` waits for
  windows, and a window whose renderer is not answering waits forever. That is what happened
  at logout: `journalctl -b -1` shows `app-neo-dsh-desktop-*.scope: Stopping timed out. Killing.`
  and then `Killing process … (neo-dsh) with signal SIGKILL`. Signals and `before-quit` go
  through `requestExit()` now: windows are destroyed rather than asked to close, the host gets
  its SIGTERM, and a 1.5 s timer forces `app.exit(0)`. Verified inside a `systemd-run --scope`
  unit — stop → `Result=success` in 868 ms, where it used to be the 90 s timeout.
- **A signal test must go through a scope, not `kill <pid>`.** Sending SIGTERM straight to the
  main process exited cleanly in 1 s even *before* this fix, because the stall only happens
  once a real renderer is in the picture; the scope is what makes it reproduce.

## Data and paths

- App home: Linux `$XDG_DATA_HOME/neo-dsh`, macOS `~/Library/Application Support/neo-dsh`;
  `DSH_HOME` outranks the stored pointer in `desktop-config.json` (Electron userData).
- The app home is seeded from `resources/` on first launch and **never overwritten**:
  `syncBundledPlugins` adds missing plugins, `copyMissingEntries` adds missing presets,
  `syncProfilePatch`-style overlay (see `src/profile-patch.mjs`) hands the shipped patch
  layer to the host as `--patch` for entries the live profile file does not already name.
  A home migrated from `~/.dsh` keeps its own files — that is how 智能批准 went missing once.
- Logs: `<home>/desktop.log` (shell + `[host stdout]`, including the plugins' audit lines);
  sessions live in `<home>/sessions/<cwd>/session-<id>/session.v3.jsonl.zstd`.
